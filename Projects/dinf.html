Data collection
infrastructurehow a vessel earns the D-INF notation, and what changes between its three qualifiers

D-INF standardizes how data moves from sensors on a vessel to a server on shore — reliably, securely, and in a form DNV can verify. It doesn't touch the source systems themselves. It governs everything downstream of them.

Reference: DNV-RU-SHIP Pt.6 Ch.11 Sec.1, built on the functional requirements in DNV-CG-0564.

Section 1.5 — Table 1

Three ways to hold the notation

Every D-INF certificate is built one of three ways. The qualifier tells you, at a glance, whether the interface is custom, proprietary-but-standardized, or built to a published protocol.

D-INF · no qualifier

Essential

A predefined set of tags from one specific source system, at a specific rate, with specific quality criteria, to one specific target. Fully customized.

  • No vessel server required
  • Proprietary protocols throughout
  • Built around a single use case
Maps to CG-0564 variant 0
D-INF(G)

Generic

A flexible set of tags from a range of different source systems. Standardized functional requirements, but the data interface itself stays proprietary.

  • Vessel server required
  • No defined external interface (may add one selectively)
  • 30-day onboard buffer minimum
Maps to CG-0564 variant 1
D-INF(S)

Standardized

Same flexible collection as Generic, but the interface follows a named standard — so any conformant client can talk to it.

  • ISO 19847 / ISO 19848, or
  • OPC UA client/server + IEC 61162-450 relay
  • Vessel server recommended in its own DMZ
Maps to CG-0564 variant 2 or 3
Section 2 — Requirements

The three certifiable components

A generic or standardized infrastructure is built from three pieces, each independently certifiable. Use the qualifier switch above — components that don't apply to your selection dim out.

01 / Onboard

Vessel server

Product Certificate

Collects data through one or more interfaces, buffers it, and serves it to local clients. May comprise several hardware components acting as one logical server. Required for Generic and Standardized; skipped entirely under Essential.

02 / In transit

Data relay component

Product Certificate

The mandatory intermediary for every qualifier — a transport network with gateways and bandwidth, or a full third-party infrastructure in its own right. Priority management for at least three traffic levels, plus an API for status, alerts, and transfer-delay logs.

03 / Onshore

Remote data server

TA or case-by-case

Receives data from potentially many vessel servers, persists at least three years of history, and serves it to remote consumers. Can be added at newbuilding or later, once collected data starts feeding other class notations.

Section 1.8 & Section 3

Getting — and keeping — the notation

Two activities are mandatory to obtain D-INF. A third exists, but only becomes mandatory once the data is actually put to use elsewhere in class.

Mandatory · 01

Document the infrastructure

Topology diagrams, function descriptions, inventory lists, bandwidth budgets, and a software change-handling procedure — submitted per component (vessel server, data relay, remote server) or as one end-to-end package.

Mandatory · 02

Survey and test on completion

An approved test programme, witnessed by a surveyor: functions and security, UPS capacity, connected source systems, communication management, master clock sync. If the remote server isn't ready yet, its tests can wait for the first annual survey.

Result

D-INF is assigned

Retained through successful annual surveys. At this point, data quality management and a cyber security management system (CSMS) are not required.

Conditional · 03

Data quality & CSMS

Becomes mandatory only once the collected, relayed data is actually used for another additional notation, an in-operation notation, or another class methodology — not for D-INF on its own.
