Overview

One shared model. Two competing ways to expose it.

These aren't three layers a request passes through in order. ISO 19848 is the data model every value is shaped into before it ever reaches a server. ISO 19847 and IEC 62541 are two alternative facets a data server can put in front of that model — a client speaks one or the other, not both stacked together.

Shared — Data model ISO 19848

Ship data — standard data channel list and format

Gives every measurement a globally unique ID, a defined structure (tabular or event), and a set of properties — unit, range, quality — so two systems that have never met can agree on what a number means. Both facets below deliver data shaped this way.

Reference architecture

Where the fork actually sits

A typical deployment has a Vessel Server pulling data in from onboard systems, and — over a Data Relay Component — a Remote Data Server exposing it ashore. Both boxes carry the same two facets, side by side, plus a legacy navigation facet on the ingest side. A consumer connects to one facet and stays there.

Notice the one crossing arrow: a server can carry ISO 19848-shaped data inside an OPC UA Read, for a consumer that only speaks OPC UA. That's still the OPC UA facet doing the work end to end — it's a payload choice within one facet, not evidence that ISO 19847 sits underneath OPC UA.

ISO 19848 — Ships and marine technology

Every measurement gets an address

Navigation equipment has long spoken a common language through the IEC 61162 series. Everything else on board — pumps, tanks, alarms, engines — historically hasn't, which is exactly the gap ISO 19848 closes: a standard way to name a data channel and describe the shape of its data, independent of who built the sensor.

Universal ID

Unique across every ship, ever

A URI built from a naming authority, a ship ID (typically the IMO number) and a Local ID. Two ships, two shipyards, one unambiguous string.

Local ID

Unique within one ship

A naming rule plus a local data name — the part a system on board actually needs to resolve a channel without knowing the whole fleet.

Short ID

Optional shorthand

A compact alternative to the Local ID, for interfaces or bandwidth-constrained links where the full path is overkill.

Build a Universal ID

The grammar, straight from the standard: UniversalID = [protocol] "//" NamingEntity ShipID LocalID
Worked from a real example in the standard's own reference material — swap in your own naming entity, IMO number and path.
Data channel property

What gets attached to every channel

Alongside the ID, ISO 19848 requires a fixed set of properties describing the channel itself — enough for a consumer to interpret a value with zero prior knowledge of the source system.

PropertyCarries
Data Channel TypeType of channel, its update cycle, and — for calculated channels — the calculation period
FormatData type and any restriction on the value (enumeration, length, range of the encoding itself)
RangeLow and high bounds the value is expected to fall within
UnitUnit symbol and the physical quantity it represents
Quality CodingWhat counts as a valid versus invalid reading — commonly drawn from OPC UA's own quality-code scheme or IEC 61162 status codes
Alert PriorityOptional — only present when the channel is used to drive an alarm
NameA human-readable description of the source system or instrument
RemarksFree text — installation location, manufacturer, and similar context
Time series data

Two shapes for the same idea: a timestamped value

Every row is called a Data Set. ISO 19848 splits time series data into two representations depending on whether the number of values arriving at a given timestamp is fixed or not.

Tabular data — a fixed-width row

Multiple raw values sampled at the same instant, or the result of a regular calculation. Because the column order is agreed in advance, a row doesn't need to repeat each channel's ID.

Alarms, status changes, manual input — anything where you can't promise a fixed number of values per timestamp. Each row must therefore carry its own Data Channel ID.

ISO 19847 — Shipboard data servers

The box that actually has to keep up

ISO 19847 sets requirements for the server that sits between shipboard machinery and the systems that want its data — collecting it, storing it, and sharing it "in a safe and efficient manner." Most of the standard is performance numbers a server has to hit.

30 / 1s
data samples per session, within one second, from ≥5 simultaneous sessions
30 days
minimum onboard storage retention
≥100
Mbit/s ethernet interface for data in and out
<5s
per session when reading 30 samples over file transport service
Getting data off the server

Three transport patterns, one server

The server must offer request-response and streaming transport, and may additionally support file transport — each tuned for a different kind of consumer, from a one-off maintenance query to a continuous condition-monitoring feed.

TransportPatternTypical consumer
Request-responseConsumer asks for up to 30 samples per session, ≥5 sessions at once, answered within 1 secondM/E condition monitoring, performance analysis, remote maintenance
StreamingServer pushes continuously — 1 session/second in, up to 2 sessions/second out, each under 1 second latencyWeather routing, optimum trim, near-real-time dashboards
File transport (FTS)Bulk read of a full data set, one session per 5 secondsVoyage data downloads, retrospective analysis

These three transports are ISO 19847's own facet — request-response, streaming and file transfer defined by the standard itself, independent of any other protocol. A server may implement a separate facet built on OPC UA (IEC 62541) instead, but OPC UA doesn't sit underneath or carry this facet — see how the two are wired side by side.

What the server has to manage

Six functions beyond moving bytes

  • 6.2
    Data managementKeeps the system clock synced to UTC, and manages the Data Channel List, Data Source Information and Alias List — registering, updating and logging every change.
  • 6.4
    Alias functionMaps one short Alias ID to one or more Local IDs, so a single request can resolve to several underlying channels at once.
  • 6.5
    Data calculationCan derive values such as min, max and average from raw channels, following the calculation data structures set out in ISO 19848.
  • 6.6
    Log managementRecords access history, status changes, configuration changes and checksum/CRC errors, kept for at least the last 30 days.
  • 5.1.4
    Condition monitoringWatches itself: system failure, storage access failure, recording interface failure, loss of UTC sync, and storage nearing capacity.
  • 5.1.6
    Access protectionRequires administrator-level authentication before management data or configuration can be changed.
IEC 62541 — OPC Unified Architecture

Not a ship standard at all — and that's the point

OPC UA comes from industrial automation, not maritime engineering. It defines an asynchronous request/response protocol, a binary and XML type system, an object-oriented information model, and a fixed catalogue of 37 standard services. The open-source open62541 library is one widely used implementation of the stack.

The information model: nodes and typed references

An OPC UA server exposes its data as a graph. Every element is a Node — one of eight NodeClasses — and every link between two nodes is a typed, directed Reference, readable as a triple: (source, reference type, target). A client can browse this graph without any prior knowledge of what's inside.

NodeClassHolds
VariableA live value — the closest analogue to an ISO 19848 data channel
VariableTypeConstrains the data type, dimensions and rank of its Variable instances
Object / ObjectTypeRepresents a system or component, and its type definition
MethodA callable function, invoked with the Call service
ReferenceTypeGives meaning to a link — e.g. HasComponent, HasProperty, HasTypeDefinition
ViewA named subset of the address space, for focused browsing
Getting connected

Three nested layers before a single Read happens

TCP connection

A stateful connection opened with a HEL/ACK handshake that agrees on basics like maximum message size. A "Reverse Connect" mode even lets the server dial out to the client.

SecureChannel

Opened on top of the TCP connection with an OpenSecureChannel exchange. Its SecurityMode is None, Sign, or Sign&Encrypt — the SecurityPolicy in force decides the actual cipher suite.

Session

Created and then activated with CreateSession / ActivateSession, so credentials — anonymous, username/password, Kerberos or X.509 — never travel in the clear.

The 37 standard services

A fixed menu — nothing bespoke

Every interaction is one of a pre-defined set of Service Sets. A client can't invent a new service; it can only call user-defined logic through the generic Call service.

Discovery

FindServers, GetEndpoints and friends — how a client learns what a server offers before it even connects.

SecureChannel & Session

Open/CloseSecureChannel, CreateSession, ActivateSession, Cancel — the connection lifecycle.

NodeManagement

AddNodes, AddReferences, DeleteNodes, DeleteReferences — building or trimming the address space at runtime.

View

Browse, BrowseNext, TranslateBrowsePathsToNodeIds — walking the graph of nodes and references.

Attribute

Read and Write — the workhorse services for pulling or pushing a Variable's current value.

MonitoredItem & Subscription

Push-style notifications on top of request/response — a client asks once, then receives changes.

Putting it together

One temperature reading, three standards

Follow a single cylinder-temperature reading from sensor to shore, and each standard's job becomes concrete.

01
ISO 19848

The reading gets a name before it gets anywhere

The sensor's value is assigned a Local ID such as main-engine/cylinder-1/temperature, wrapped into a Universal ID with the ship's IMO number, and given a Property block: unit °C, valid range, quality coding, update cycle.

02
ISO 19848

It's shaped into a Data Set

Because it's one of many channels sampled together every second, it lands in a Tabular Data row alongside the other engine channels — timestamp first, then values in the agreed column order.

03
ISO 19847

The shipboard data server takes custody

It ingests the row within its 30-samples-per-second budget, timestamps it against a UTC-synced clock, writes it to at least 30 days of storage, and logs the write in its system log.

04
Fork — pick one facet

A shore application asks for it, one way or the other

The remote data server offers the same buffered reading through two independent facets. The consumer's own protocol stack decides which one it speaks — not the data itself, which is identically ISO 19848-shaped either way.

05a
ISO 19847 facet

Path A — native request-response

A performance-analysis tool opens a request-response session and asks for the last 30 samples of that channel — one of up to five sessions the server must be able to serve at once, inside one second. No OPC UA involved.

05b
OPC UA facet

Path B — an OPC UA Read

An OPC UA client instead opens a SecureChannel and an authenticated Session, then calls the Attribute service's Read against the Variable Node that mirrors the same ISO 19848 channel. No ISO 19847 request-response involved.
